# KirinYT 1.9.5.3 Beta

Pre-release · 15 October 2026 (MYT)

## Bilibili: aria2 HTTP 503 recovery

- Fix the recovery detector missing aria2's `The response status is not successful. status=503` message. It previously recognized yt-dlp's `HTTP Error 503` spelling only, so a failed video could stop at attempt 0 despite an available API-provided backup.
- Recognize HTTP 403, 410 and 5xx responses from either downloader. After a failed media transfer, refresh extraction and use the existing bounded CDN recovery. A subsequent successful audio download does not erase the earlier video failure.
- Recognize aria2's HTTP 429 and 451 diagnostics as non-retryable restrictions, even when another connection logged a transient failure. An unexplained aria2 exit code 29 is not automatically retried, since it can represent other HTTP failures.
- Preserve the selected video/audio IDs, cookies, output directory, downloader and existing partial-download handling. Retry only after media extraction; stop after the existing mirror limit or user cancellation.

## Validation

- Seven new Android recovery regressions cover the reported 503/video-failure/audio-success sequence, native and aria2 HTTP spellings, non-retryable restrictions, misleading URL parameters, API errors before extraction, exhausted mirrors and cancellation.
- 21 Android tests in total include the previous recovery and format-recommendation tests.
- 20 Python engine tests include a local HTTP server returning 503 for video while audio finishes; a subsequent mirror attempt produces the original video bytes and a merged file with both streams. The interrupted/resumed download regression remains enabled.
- Release workflows run both suites and verify all APK signatures before publication.

## What the report establishes

The reported `BV19rWw6xENu?p=1` attempt selected `30080+30280`; the video server returned 503 while the 9.33 MiB audio completed. This failure is a transfer failure, not evidence of a video-length limit or an AV1 playback problem. This patch fixes the missed recovery trigger; it cannot guarantee that a public CDN or its backup will always be reachable, and it does not repair previously damaged files.

After updating, retry the Bilibili link. If the primary media server fails with 503 again, the log should now show a retry message and `attempt=1` when fresh extraction succeeds. If every available server fails, the download still reports an error instead of claiming success.
